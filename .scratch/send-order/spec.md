# Приём заявки

Status: ready-for-agent

## Problem Statement

Сайт «Кварты» уже просит человека оставить заявку, но никуда её не сохраняет. Нужен сервер, который принимает заявку и кладёт её в PostgreSQL. Форма на сайте в этом срезе не подключается.

## Solution

В том же репозитории появляется серверный пакет на Hono с RPC-типами, Drizzle и одной командой сохранения. Сайт переезжает в пакет website и получает зависимость на эти типы, но форма остаётся макетом. Локально Docker поднимает только PostgreSQL. Сервер запускается отдельно на хосте.

## User Stories

3. Как человек, оставляющий заявку, я хочу, чтобы написанная заметка сохранилась вместе с именем и телефоном, чтобы было видно, что я хотел уточнить.
4. Как человек, оставляющий заявку, я хочу, чтобы заметка из одних пробелов сохранилась как пустая, чтобы пустое поле не стало текстом.
5. Как человек, оставляющий заявку, я хочу, чтобы пробелы по краям имени и заметки не сохранялись, чтобы в базе лежал сам текст.
6. Как человек, оставляющий заявку, я хочу, чтобы пустое имя отклонялось и ничего не записывалось, чтобы заявка без имени не появлялась.
7. Как человек, оставляющий заявку, я хочу, чтобы имя длиннее 200 символов отклонялось и ничего не записывалось, чтобы слишком длинное имя не сохранялось частично.
8. Как человек, оставляющий заявку, я хочу, чтобы заметка длиннее 2000 символов отклонялась и ничего не записывалось, чтобы слишком длинная заметка не сохранялась частично.
9. Как человек, оставляющий заявку, я хочу, чтобы телефон сохранился как E.164, чтобы номер имел один международный вид.
10. Как человек, оставляющий заявку, я хочу, чтобы действительный городской номер Беларуси принимался так же, как мобильный, чтобы меня не заставляли присылать только мобильный.
11. Как человек, оставляющий заявку, я хочу, чтобы номер не из Беларуси или недействительный номер отклонялся и ничего не записывалось, чтобы в базе не было плохого телефона.

13. Как человек, оставляющий заявку, я хочу, чтобы повтор с тем же id обновил имя, телефон и заметку, чтобы исправление заменило прежние контакты.
14. Как человек, оставляющий заявку, я хочу, чтобы время создания не менялось при повторе, чтобы было видно, когда заявка появилась впервые.
15. Как человек, оставляющий заявку, я хочу, чтобы время изменения обновлялось при каждом успешном сохранении, даже если имя, телефон и заметка те же, чтобы было видно последнюю успешную отправку.
16. Как человек в другом браузере, я хочу, чтобы новый id создал другую заявку, даже с тем же телефоном, чтобы телефон не склеивал чужие заявки.
17. Как человек, оставляющий заявку, я хочу, чтобы знание моего id позволяло обновить эту заявку без входа, чтобы повторная отправка из того же браузера работала без учётки.
18. Как человек, оставляющий заявку, я хочу приложить аналитику к первой успешной отправке, чтобы первые данные визита сохранились.

20. Как человек, оставляющий заявку, я хочу отправить заявку без аналитики, чтобы контакты сохранились и аналитика осталась пустой.

27. Как сайт, я хочу получить код обновления, если два создания с одним id пришли одновременно и второе догнало уже созданную строку, чтобы гонка не выглядела сбоем.
28. Как сайт, я хочу получить отдельный код для пустого или слишком длинного id, для не-строки и для отсутствующего id, чтобы отличить плохой id от плохого телефона.
29. Как сайт, я хочу получить отдельный код для плохого имени, чтобы показать ошибку имени.

33. Как сайт, я хочу присылать лишние поля верхнего уровня и не получать из-за них отказ, чтобы сервер их просто не записывал.

36. Как сайт, я хочу импортировать тип маршрута из серверного пакета, чтобы тело и коды ответов были теми же, что на сервере.
37. Как сайт, я хочу, чтобы браузерный origin из настройки сервера проходил CORS, чтобы будущий вызов из браузера не упёрся в чужой origin.
38. Как разработчик, я хочу поднять локальный PostgreSQL одной командой compose, чтобы сервер мог к нему подключиться без установки базы в систему.
39. Как разработчик, я хочу применять миграции отдельной командой, чтобы схема не менялась сама при старте сервера.
40. Как разработчик, я хочу запускать Hono на хосте, чтобы контейнер базы не содержал сервер.

42. Как разработчик, я хочу, чтобы перенос сайта не менял форму заявки, чтобы макет по-прежнему не отправлял данные.

## Implementation Decisions

- Репозиторий становится pnpm workspace из двух пакетов: website и order-server. Website — нынешний сайт. Order-server — новый сервер.
- Сервер — Hono по шаблону Node, с `@hono/node-server`. Не edge и не Cloudflare Workers.
- Конец-в-конец типизация — родной RPC Hono: сервер экспортирует тип приложения, website зависит от пакета order-server и может импортировать этот тип. Отдельной генерации клиента и предварительной сборки деклараций нет.
- Вход маршрута описывает zod через `@hono/zod-validator`. Коды ответов выводятся из того же маршрута.
- Единственный маршрут — `POST /send-order`.
- Тело запроса: обязательные `id`, `name`, `phone`; необязательные `note` и `analytics`. Отсутствующий ключ `note` или `analytics` равен `null`. Неизвестные поля верхнего уровня отбрасываются.
- Успех — HTTP 200 и тело `{ code }`. Новая строка — `CREATED`. Существующая строка — `UPDATED`. Id в ответе нет.
- Отказ проверки — HTTP 400 и тело `{ code }`. Коды: `INVALID_ID`, `INVALID_NAME`, `INVALID_PHONE_NUMBER`, `INVALID_NOTE`. При любом из них строка не меняется.
- Неожиданный сбой — HTTP 500 и `{ code: "INTERNAL_SERVER_ERROR" }`.
- Кодов `INVALID_ANALYTICS` и `INVALID_BODY` нет.
- `id` — строка от 1 до 128 символов включительно, колонка `text`. Сервер хранит её как пришла, без обрезки и без проверки формата UUID. Пустая строка, не-строка и строка длиннее 128 символов — `INVALID_ID`.
- Повтор с тем же id обновляет `name`, `phone`, `note` и время изменения. Если два создания с одним id сталкиваются, второе обновляет строку и возвращает `UPDATED`.
- `name` обрезается по краям. После обрезки имя должно быть непустым и не длиннее 200 символов, иначе `INVALID_NAME`.
- `phone` проверяет `libphonenumber-js` для региона BY. Годится любой действительный белорусский номер, не только мобильный. В базу пишется E.164. Иначе `INVALID_PHONE_NUMBER`. Телефон не уникален.
- `note` обрезается по краям. Пустая заметка и заметка из одних пробелов хранятся как `null`. Длиннее 2000 символов — `INVALID_NOTE`.
- `analytics` — `jsonb`, по умолчанию `null`. Записывается только пока в базе `null` и в запросе пришёл непустой объект размером не больше 8192 байт UTF-8 у `JSON.stringify`. Пустой объект, `null`, отсутствие, массив, строка, число и объект больше этого размера не записываются и не вызывают ошибку. Уже записанный объект не заменяется. Ключи внутри не проверяются и не дополняются.
- Таблица называется `records`. Колонки: `id` text, первичный ключ; `name` text, не null; `phone` text, не null; `note` text, null; `analytics` jsonb, null; `created_at` и `updated_at` timestamptz, не null. Время ставит PostgreSQL, часы клиента не принимаются. `created_at` после вставки не меняется. `updated_at` меняется при каждом успешном сохранении.
- Схема — SQL-миграции Drizzle в репозитории. Их применяет отдельная команда, не старт сервера.
- В корне репозитория compose поднимает только `postgres:17-alpine`, порт 5432, база `kvarta`, пользователь `kvarta`, пароль `kvarta`, данные в volume. Сервера в compose нет.
- Сервер слушает порт из `PORT`, по умолчанию 3000. Его запускают на хосте отдельно.
- `DATABASE_URL`, `WEB_ORIGIN` и `PORT` читаются из окружения пакета order-server. Локальный `DATABASE_URL` указывает на `postgresql://kvarta:kvarta@localhost:5432/kvarta`. Локальный `WEB_ORIGIN` — `http://localhost:4321`. В git попадает только пример, не заполненный секретный файл.
- CORS разрешает origin из `WEB_ORIGIN`.
- Списка заявок, кабинета, лимита запросов и тестов нет.
- Пакет website после переноса зависит от order-server. Форма заявки, её состояния и страницы не меняются.

## Testing Decisions

Автоматических тестов в этом срезе нет. Это решение, а не пропуск: тесты маршрута предлагались и были отклонены.

В репозитории сейчас нет тестового раннера и нет похожих тестов. Добавлять шов ради этого среза не нужно.

Если тесты появятся позже, хороший тест проверяет только внешнее поведение `POST /send-order`: код ответа и то, какая заявка в итоге прочитана из базы. Не проверяются внутренности zod, SQL и порядок вызовов. Такой шов сейчас не создаётся.

## Out of Scope

- Подключение формы к серверу, экраны успеха и ошибки, хранение id в браузере.
- Поле email.
- Чтение списка заявок и любой кабинет.
- Каталог, оплата и заказ как отдельная сущность. Заявка не становится заказом.
- Лимит запросов и учётная запись.
- Автоматические тесты.
- Docker для Hono и Docker для сайта.
- Замена уже записанной аналитики.
- Генерация id на сервере и проверка, что строка похожа на UUID.

## Further Notes

Словарь проекта: заявка, заметка, аналитика, телефон. Слова «заказ», «лид», «комментарий», «источник» и «utm» для этих понятий не используются, даже хотя маршрут называется `/send-order`, пакет — order-server, а таблица — `records`.

Причины имён и правил записаны в глоссарии и в трёх ADR: идентичность заявки задаёт браузер, аналитика пишется один раз, таблица заявки называется records.
